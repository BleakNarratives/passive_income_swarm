[P0-1] ROTATE THE WALLET CONNECTION
--------------------------------------------------------------------------------
  Why it must be you:
    keys/nwc.secret holds a nostr+walletconnect:// URI. That format contains a
    `secret=` field which authorises PAYING INVOICES from your wallet — it is a
    spending credential, not a read-only one. It was committed to this PUBLIC
    repository on 2026-04-30 (commit 3f4ad07) and has been readable by anyone
    since. There is no way for me to revoke it: revocation lives in the wallet
    provider's account UI, behind your login.

    I checked whether an API path exists. coinos does not expose account-level
    NWC revocation without an authenticated session, and creating a replacement
    wallet programmatically requires email verification and a human-owned
    account. No workaround exists. This one is genuinely yours.

  What I already did:
    - Removed it from the git index (content preserved on disk, not deleted).
    - .gitignore corrected so it cannot be re-added by accident.
    - Documented rotation + history-purge in SECURITY.md.
    - Pinned a sha256 fingerprint of the leaked value in swarm/readiness.py so
      the system can tell you "you are still using the compromised credential"
      without ever storing or printing the credential itself.
    - `swarmctl readiness` reports this as blocked right now. Confirmed.

  Exactly what to do:
    1. Log in to coinos (or whichever wallet that URI belongs to).
    2. Find Nostr Wallet Connect / connected apps.
    3. Revoke the existing connection.
    4. Create a new one. Copy the new URI.
    5. Replace keys/nwc.secret with it as a single line, then:
           chmod 600 keys/nwc.secret
       (0644 today — every other user on that machine can read it too.)
    6. Run: bash ./swarmctl readiness
       It must stop saying "still the credential that was public since 2026-04-30".

  How you know it worked:
    readiness shows  nwc_credential  ready  present, rotated, mode 600

  Time: 5 minutes. Do this one before the others; everything else can wait.

[P1-1] RESTORE OR AUTHORISE THE SIGNING IDENTITY
--------------------------------------------------------------------------------
  Why it must be you:
    keys/nostr.key DOES NOT EXIST. keys/nostr.pub does. So the worker has a public
    identity and no way to sign an event — it cannot publish a job result, which
    means it cannot earn anything at all, regardless of everything else being
    green.

    I could generate a new secp256k1 keypair in one command and the worker would
    run. That is not the question. The question is whether you want a NEW identity
    with zero history or the EXISTING npub that customers may already follow. I
    do not know where the original nsec lives. Generating a replacement without
    asking would silently discard an identity, and that is your call, not mine.

  Choose one:
    (a) You have the nsec: put it in keys/nostr.key, chmod 600. Identity preserved.
    (b) You do not care about the old npub: tell me, and I generate a fresh
        keypair, print only the npub, and write the secret at 0600. You lose any
        reputation attached to the old identity.

  Verify: bash ./swarmctl readiness  ->  signing_key  ready  present

  Time: 1 minute if you have the nsec.
